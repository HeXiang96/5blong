# v2.0 方案：从「6 人房」到「20 人房」

> 2026-10-28 · 状态：**待业主拍板，未改任何源码**

---

## 一、结论

v2.0 我建议只做一件事：**把语音从「全互联 mesh」换成「混合转发」**，让 10 人以上的房间真正能用。

不加新功能。**加新功能撑不起 2.0，也救不了这个产品最硬的伤。**

理由是：现在这个天花板不是"还能再优化"，而是**架构决定的**，而且代码注释里自己写明了。

---

## 二、为什么是这个问题（三条证据）

### 证据 1：产品的核心承诺自己打了自己

README 第一行写着「低延迟语音为核心的临时沟通工具」，紧接着写「**单房建议 2–6 人，最多 13 人**」。

而开黑圈是 **5v5**，代码注释写着「支持 20 人」。

> 一个让 10 个人开黑的产品，语音却建议 6 人以内。

### 证据 2：瓶颈不是带宽，是每台机器自己

`protocol.ts:1070` 的注释写得很直白：

```
全互联 mesh 的边数是 n(n-1)/2，13 人即 78 条媒体连接，
平均每个客户端上行 12 路 Opus（每路 64kbps，合计约 0.77Mbps）
—— 带宽不是瓶颈，瓶颈是"每人都要给 12 个人编码"。
```

0.5 Mbps 不算什么，**12 路并行编码 + 12 路解码才是**。弱一点的机器、或者边上还开着游戏，当场就掉。

### 证据 3：线上实测已经撞上了

房号 009706（9 人房）的遥测：

| | RTT | 丢包 |
|---|---|---|
| 房主 | 21ms | 0% |
| 其余 6 人 | 357–437ms | 4.1–6.2% |
| 已离开的人（离开前） | 30–57ms | 0% |

**房主的网络是好的，离开的人的网络也是好的，只有在房的人之间全是 400ms + 5%。** 这不是某个人的网差，是 mesh 在 9 个人时的常态。

## 三、三条路线对比

| | **A. 语音混合转发**（推荐） | B. 补半成品 | C. 产品形态升级 |
|---|---|---|---|
| 解决什么 | 10 人以上不卡；人数上限提到 20 | 移动端、单人共享、房间回访 | 房间变"常驻空间" |
| 能对外说的一句话 | **「一间房，20 个人一起说话」** | 说不出一句 | 「5blong 变成熟了」 |
| 改动面 | 语音媒体通道（信令/UI 不动） | 散在十几处 | 数据模型 + 全站文案 |
| 风险 | 音质/延迟可能略降 | 低 | **和"临时房"定位冲突** |
| 我的判断 | **做** | 塞进 2.1/2.2 | 不做 |

B 和 C 我都不建议放进 2.0：B 是"该做的日常"，C 会把你往熟人社交拽（你自己刚否掉好友增强，方向是一致的）。

## 四、推荐方案：混合转发，而不是推翻重来

### 核心做法

```
房间 ≤ 4 人   → 保持 P2P mesh（音质最好、零成本、延迟最低）
房间 ≥ 5 人   → 自动切 SFU 转发（每人只发 1 路，SFU 分发）
```

**这正是屏幕共享已经在用的策略**（观众 ≤4 直连、≥5 走 SFU），已经跑了几个月，验证过。

### 为什么这次不是"从零造一个 SFU"

| 已验证的东西 | 在哪 |
|---|---|
| Cloudflare Realtime SFU 的会话/发布/订阅全流程 | `screen-share.ts`（发布 + 订阅两条路径都通了） |
| SFU 同域代理、TURN 凭据现签 | `worker/_worker.pages.js` 的 `/sfu`、`/ice` |
| 音频轨走 SFU | 已经在发 `trackNameAudio`（共享系统声音） |
| 订阅端按人控制音量/闭听 | 本地播放层，不受传输方式影响 |

所以 v2.0 的活是：**把「屏幕共享那套 SFU 客户端」扩成「语音也能用」，并做房间内的成员级订阅管理**。不是新基础设施。

### 要改的地方（按风险排）

1. **发布**：本地麦克风轨发到 SFU，替代"给每个成员各拨一次 call"
2. **订阅**：按成员 id 订阅他的音频轨，维护 `member ↔ track` 映射（进人订阅、走人退订）
3. **说话检测**：现在基于本地 WebAudio 分析自己的流，**不受影响**；别人的说话状态从音频轨的电平判断，要重新接
4. **断线重连**：现有的"自愈 3 次 + 中继降级"是 PeerJS 那套，SFU 要写新的
5. **静音/踢人**：走信令，不变；但要保证 SFU 那边同步停发

第 4 条是最容易出问题的地方，也是必须做灰度的地方。

### 灰度方式

不要一次切全量。按房间人数分档放：

1. 先在 **5–8 人房**启用，观察一周（这类房现在最难受，收益最明显）
2. 再放到 **9–13 人**
3. 最后才考虑把上限从 13 提到 20（**建议这一步单独一个版本，别和切换混在一起**）

出问题一条开关退回 P2P——**必须有这个开关**，不能只有"改代码回滚"。

## 五、风险与止损

| 风险 | 说明 | 止损 |
|---|---|---|
| **音质变差** | SFU 用的还是 Opus，但多一次转发，编码参数可能和现在不同 | 小房间继续 P2P，音质问题只影响大房 |
| **延迟增加** | SFU 是跨境转发，可能 +50–150ms | 大房间本来延迟就高；用现有"延迟档位"让用户自己选 |
| **费用** | Cloudflare SFU 有免费额度，超了按用量 | 先只对大房启用，用量可控；监控每日分钟数 |
| **说话检测不准** | 现在按本地电平，切 SFU 后别人的电平要重算 | 上线前专门验一轮；不准就先退回"固定光环" |
| **13→20 人挤一块** | 一次改两件事，出问题分不清原因 | **分版本**：切传输一个版本，提上限另一个版本 |

## 七、需要你拍板

1. **2.0 就做「20 人房」这一件事，不加新功能**——同意吗？
   - 我的理由：这是唯一"不做就会撞墙"的；其他都是锦上添花，放 2.1 更合适。

2. **人数上限提到多少？**
   - 13 → 20：够 5v5 + 待分队，但 SFU 转发量和费用都上去
   - 13 不动，只解决"9 人也不卡"：风险最小，但对外说不出新东西
   - 我的建议：**先只解决卡，上限下一版再提**。

3. **要不要保留"小房间走 P2P"？**
   - 我的建议：**保留**。2–3 人时 P2P 的音质和延迟确实更好，没必要为了统一而牺牲。

## 八、如果同意，我下一步做什么

**不直接改代码。** 先做一个「双通道对照实验」：

在一间 8 人房里，一半人走 P2P、一半人走 SFU，用现有遥测对比 RTT、丢包、卡顿、CPU。
拿到数据再决定切不切——因为这套东西改错了是**整房没声音**，比画面糊严重得多。

这个实验用现有代码就能做，不需要动产品。
