# 语音房内「梗王对局」接入方案

> 2026-11-04 · 状态：待拍板（未改任何 src 代码）
> 先看能点的演示：`tests/fixtures/duel-in-room.html`（纯前端单文件，52KB，零依赖，`#menu` / `#duel` / `#mid` 三个入口可直接跳状态）

## 0. 结论先行

不新建页面、不新建房间、不动美术资源。做法是三件事：

1. **入口**：成员卡里加一个按钮（现有「戳一戳/投喂」那排下面），点对方 → 「发起梗王对局」。
2. **覆盖**：房间场景整体压暗一层（约 40% 黑 + 1.5px 模糊，要的是"略黑"不是全黑），对局 HUD 叠在上面。
3. **复用**：两只猪就是房间里原有的那两只，用 `transform` 位移到左右两侧当"棋盘两端"，对局结束回原位。**不新增角色、不换背景。**

一句话：**房间是底图，对局是浮层，猪是棋子。**

## 1. 交互流程（状态机）

```
idle ──点猪──▶ menu ──点「梗王对局」──▶ inviting (TTL 30s)
                                            │
                    ┌──── 拒绝/超时 ────────┘
                    │
                accepted ──3-2-1 倒数──▶ starting ──发牌──▶ playing
                                                            │
                               ┌──── 一方血量 ≤0 / 退出 ────┤
                               ▼                            │
                            ended ◀───────────────────────┘
                               │
                            回房间（还原猪位置、清空浮层）
```

时序（两人视角）：

| 步 | A（发起方） | B（被邀请方） | 房间其它人 |
|---|---|---|---|
| 1 | 点 B 的猪 → 成员卡 → 梗王对局 | — | — |
| 2 | 顶部 toast「已发出邀请」，30s 倒计时 | 右上方弹邀请卡（接受 / 拒绝 / 30s 自动取消） | 无感 |
| 3 | 收到接受 → 3-2-1 | 点接受 → 3-2-1 | 顶部小提示「A 和 B 开了一局」 |
| 4 | 房间压暗、猪位移、发牌 | 同左 | 可围观（只读） |
| 5 | 打牌、结束回合 | 同左 | 看战报 |
| 6 | 结算 → 回房间 | 同左 | 浮层收起 |

## 2. 视觉分层（z-index 表）

| 层 | 内容 | 说明 |
|---|---|---|
| z-0 | 天空 / 太阳 / 云 / 山丘 / 草地 | 原样，不换主题 |
| z-20 | 压暗层 `rgba(14,10,18,.46)` + `backdrop-filter: blur(1.5px)` | 唯一"略黑"手段，退场 0.6s 淡出 |
| z-25 | 篝火 | 保持在中间，天然当"中线" |
| z-30 | 两只猪（原组件 + transform） | 左 `left:9%` / 右 `right:9%`；过渡 1.1s 弹性曲线 |
| z-31 | 随从排（左/右各一排） | 站在猪与篝火之间，`bottom:29%`，带地影 |
| z-40 | 血量条 / 战报 | 血量条贴在猪头顶上方 |
| z-45 | 手牌抽屉 | `bottom:66px`，最多 8 张，超出横向滚动 |
| z-46 | 操作条（退出 / 当前回合 / 结束回合） | 在底栏原位置之上 |
| z-60 | 成员卡、邀请卡 | 与现有层级一致 |
| z-75 | 结算卡 | 回到房间按钮 |

关键点：

- **猪不能重建**。用外层绝对定位容器 + `transform`，不改动现有 flex 布局，避免把房间布局搞塌。
- 对局中**淡出底部按钮栏**（静音/分享/闭听/聊天/结束房间），否则手牌永远压在按钮上；结束对局再淡入。
- 手牌永远在猪的下方视觉区，随从永远在手牌上方，两者不重叠（演示里踩过这个坑，已修）。

## 3. 玩法（针对"纯靠运气"的处理）

| 维度 | 做法 | 理由 |
|---|---|---|
| 资源 | 每回合法力上限 +1，上限 10 | 炉石式节奏，前 3 回合不会一波流 |
| 手牌 | 起手 3 张，每回合抽 1，上限 8 | 手牌溢出会烧牌，逼着出牌 |
| 牌组 | 各 14 张，**等预算配平** | 大东彦=爆发（8 伤终结、AoE），Renai=续航（回血、抽牌、减攻）；避免"对面四张 UR 你四张 N" |
| 起手 | 3 张 + **一次换牌** | 对起手坏掉的方差兜底（演示版省略，正式版加） |
| 胜负 | 30 血归零 / 牌库抽干进疲劳（1、2、3…递增） | 疲劳保证局不会无限拖 |
| 单局时长 | 目标 4–6 分钟，14 张牌库 ≈ 12–15 回合 | 语音房里不能开半小时的局 |
| 随机 | **只由一个种子决定**（房主生成下发） | P2P 双方各自 `Math.random()` 一定不同步，这是硬伤 |

随从/法术机制（首版只做这些，够玩了）：嘲讽、封号（下回合不能攻击）、战吼、法术伤害、群体伤害、回血、抽牌、减攻、压缩对手法力、英雄技能（2 费）。

## 4. 网络与权威（复用现有基建）

现有代码里已经有两条可直接抄的路子：

- `src/client/game/game-mesh.ts`：独立的对局子系统，`HostToGuest` / `GuestToHost` 消息对，**不引用语音房协议**。
- `src/client/voice/use-voice.ts` 的猪圈事件：**房主统一下发，所有端看到同一件事**——对局状态就该这么走。

建议：

```
duel:invite   { from, to }                       邀请
duel:decline  { from }                           拒绝
duel:accept   { from }                           接受
duel:start    { seed, decks:[a,b], first }       房主下发：种子 + 双方牌组 + 先手
duel:action   { kind:"play"|"attack"|"end"|"power", payload }   访客只发"意图"
duel:state    { snapshot }                       房主广播权威快照（每回合 / 每次结算）
duel:end      { winner, reason }                 胜者、原因（血空 / 退出 / 掉线）
```

规则：

- **房主是唯一状态源**。访客不自己算血量，只做"发意图 + 播动画 + 等快照"。
- 发牌用 `seed` 走 PRNG（mulberry32 一类 20 行实现），双方牌序必然一致。
- 围观者订阅 `duel:state`，只读。
- 断线：访客掉线给 10s 宽限，超时判负；房主掉线直接中止（回房间，不算战绩）。首版不做断线续局。

- **不做**：动画特效、卡牌合成、商店、排名赛季、断线续局、多语言。
- **不做**：把对局做成独立窗口。独立窗口会丢掉"几个人在一个房间里围观聊天"的氛围，那是这个功能唯一的差异化。

## 9. 对语音链路的影响评估（房主最关心的那条）

**结论：不影响。开打之后语音照常，两个人可以一边打牌一边骂。**

原因（按你们现有实现）：

| 关注点 | 实际情况 |
|---|---|
| 语音协商 / 握手 | 音频走的是 `MediaConnection`（独立的 RTCPeerConnection + audio track）。对局只发**应用层数据消息**，不重协商 SDP、不改 codec、不触发 ICE restart。 |
| 信令 | 方案 A（推荐）**零新增信令**：duel 消息挂现存的那条 `DataConnection`（现在 chat / roster / 笔迹都走它）。方案 B（独立 duel Peer）会多一条信令握手，但走同一套 signal 服务、与房间音频连接互不相干——开黑圈现在就是这么干的。 |
| 音频状态 | 对局**不碰** `muted` / `deafened` / 闭听 / 麦序。压暗只是视觉层，`<audio>` 一个都不动。 |
| CPU / GPU | 对局是纯 DOM + CSS，没有 canvas / WebGL / 音频解码。Tauri 同一个 webview，不新开窗口、不新开进程。 |
| 带宽 | 每回合 1 次状态快照（几百字节 ~ 几 KB），对面 Opus 语音约 32kbps，量级差两个数量级。 |

真正需要盯的 4 个点（都不是"会不会断"，而是"别自己写坏"）：

1. 对局 UI 里**不要顺手调用** engine 的 mute / deafen / 停麦——一调就是"打牌把麦关了"的 bug。
2. 消息频率控制：只在回合切换 / 结算时发快照，别做逐帧同步。
3. 若选独立 duel Peer：对局结束必须 `peer.destroy()`，否则每局泄漏一条连接。
4. `backdrop-filter` 别铺满全屏——低端机 GPU 吃紧会掉帧，但**音频仍不受影响**（WebRTC 音频在独立线程）。真遇到掉帧就降级成纯半透明遮罩。

验证方式（10 分钟能做完）：

- 开一局的同时看 `session-stats` 里的音频码率曲线 / `chrome://webrtc-internals` 的 `bytesReceived` 是否持续增长；
- 对局中互相说话，确认没有断续、没有回声；
- 对局结束后检查 Peer 数量是否回到开局前（`duel:end` 后连接该关的关）。
