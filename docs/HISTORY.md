## 最近更新（2026-11-03 深夜 · 1.9.20 已发）：自建协商四补丁 + 终极根因（中继配额）

### ★ 终极根因：coturn 的 `user-quota=12`

一整天所有"玄学"（进不去房、听不到、时好时坏、重进几次就好）的底层原因：
**每人凭据最多 12 条中继分配**，重拨几轮就打满 → 后续分配全被拒（30 分钟 622 次
`error 486`）→ 跨网只能靠中继 → 永远连不上。"重进有效" = 新凭据重置配额。
已改 `256` / 总配额 `2400`，**立即对全部客户端版本生效**。

### 🐞 进房后"重连一两分钟"（1.9.19 实测）：自建协商的三处时序缺陷

链路其实 ~20 秒就通了（诊断：`pk=20` 与 `link=failed` 并存），卡住的是三件事：

1. **僵尸链路吞 offer**：任何 `rtc-*` 消息都会建链，一条迟到的 `rtc-bye` 就能
   以错误角色造出"closed、无 PC"的僵尸，它留在表里把后续 offer 全部吞掉
   （`handle` 的 closed 守卫直接 return），answer 永远不来、双方毫无痕迹。
   → 只对 `rtc-offer` 建链；offer 到达时僵尸删掉重建。
2. **迟到的失败覆盖已连接**：自建腿 12~18s 超时报 failed 时无条件覆盖状态，
   哪怕回落 PeerJS 的腿已经连上。→ 已连接时不覆盖，只记事件。
3. **异常全部静默**：`handle` 的 catch 吞掉一切，answer 生成失败零痕迹。
   → 新增 `onEvent` 回调，每一步失败写进诊断 `events`。

### 🔧 "等包判死"优化（业主实测"反复断开又自动重连"）

ICE 通了却 14 秒没有音频包（真单通）时，原实现拆腿重拨——但重拨走同样的路由
治不了单通，只会制造"断开→重连→又断"循环。改为：保持连接 + 每 3 秒低频复查，
包一来立刻转成功；怀疑写进诊断。

### 🛡 防递归护栏

自建协商回落 PeerJS 时未先标记 `dcFallback`：数据通道若未就绪，
`callPeer → startDcOffer → callPeer` 会无限递归（栈溢出）。回落前先标记。

**回归**：402 项单测全绿（+6：僵尸重建、非 offer 不建链、状态不覆盖、
失败上报 ×2、僵尸消息上报）。1.9.20 已推送。

### 🎯 1.9.21：answer 消失的**终极根因**修掉（1.9.20 事件日志首次出手即定案）

进房诊断 `events` 抓到铁证（江南房主端）：

```
answer 端处理 rtc-offer 失败：Failed to set local answer sdp:
Called in wrong state: stable
```

根因：`negotiate()` / `answerTo()` 把 localDescription **设了两次**——
第一次原始 SDP、第二次整形（opus 参数）后的 SDP。**answer 方的第二次非法**
（PC 已回 stable），抛错被旧版 catch 吞掉 → answer 从未成功发出过 →
自建协商上线以来**每一次都必然失败**，全靠 12~18s 超时回落 PeerJS。

**修法**：整形提前到 `setLocalDescription` 之前、**只设一次**（两端一致）。

修完预期：自建协商首次真正端到端工作——房主↔访客**几秒连上**，
不再有 12~18s 超时、不再回落、不再产生僵尸。
**回归**：404 项单测全绿（+2：两端各断言 `setLocalDescription` 只调一次）。
1.9.21 已推送（tag `app-v1.9.21`）。

## 最近更新（2026-11-03 · 待发 1.9.19）：一整天的语音链路大修

> 这一天所有故障都指向同一件事：**媒体协商只有一条命**。
> 下面按层分开写，因为它们是三件不同的事，修法也完全不同。

### 一、信令层（决定"能不能进房、谁在哪个房"）

**信令服务已换成我们自己的。** 从 npm `peer` 包移植回 CF 时代那套 `SignalHub`
（`server/src/signal.mjs`，systemd `5blong-signal-node`，绑 127.0.0.1:9001，
nginx 的 `/peerjs` 反代到它）。客户端零改动——地址还是 `wss://5blong.site/peerjs`。

| 改了什么 | 为什么 |
|---|---|
| 删掉公共云兜底 `0.peerjs.com` | 兜底过去的人是"三无用户"：能建房，但 `/ice` 拿不到、中继不通、后台查无此房（702621 实测：全站访问日志 0 命中，排错一整天都在错方向）。两条线路还是**互不相通的注册表** |
| OFFER 暂存 2.5 秒重投 | 房主刚好在重连那 1~2 秒，消息不丢，人一回来立刻补投；压不住才回 `EXPIRE` |
| `ROOM-SNAPSHOT` 回到信令 | CF 时代房主就是这么上报的，1.9.12 换包后断了才改 HTTP。服务端收到后转交 API 入库，入库逻辑复用一份 |
| 判死时间 60s → 180s（服务端） | 心跳 5 秒一次但跑主线程，标签页进后台被压到约 60 秒/次，正好踩线。实测同一个人同房号 25 分钟重新注册 6 次 |
| 断开时用 WeakMap 取回 id | `disconnect` 里 `client.getId()` 可能已取不到，在线房号永远删不掉（面板会一直显示已关掉的房） |
| 重拨留间隔（1.2s / 3s） | 原来 1~2 秒内连拨三次就判死，房主正在重连也等不到 |
| 房主信令掉线时自己能看到提示 | 不再出现"我明明建了房却没人进得来"，双方各说各话 |
| 修 `reconnect()` 后重复挂监听 | 每重连一次，connection/call/disconnected 监听翻一倍 |
| 线路轮换 `routeAt(start, attempt)` | 支持"从任意线路起步"轮换。公共云兜底删除后生产只剩一条线路，此函数保留——将来加国内备用节点时直接可用（有单测钉住） |

### 二、媒体协商层（决定"进房后有没有声音"）

**核心改动：房主 ↔ 访客这条腿不再走 PeerJS 的 `call/answer`。**
新增 `src/client/voice/media-link.ts`：自己 `new RTCPeerConnection`、自己生成
offer/answer，SDP 与 ICE 候选**走两人之间已有的数据通道**（有序、有重传、人在房里就说明它通），
answer 超时自动重发（最多 2 次），迟到候选缓存。

> 为什么：信令日志实测每一条 OFFER 都在 **100~120ms** 内拿到 ANSWER，
> 候选也齐全（host / srflx / **relay** 都有），但连接仍然停在 `new` 或被 9 秒看门狗拆掉。
> 根因是 PeerJS 把 SDP 交给信令**转发一次**——丢一条，这条腿就永远起不来。

- 只改「房主 ↔ 访客」（只有他们有数据通道）；访客之间仍走 PeerJS；
- 对端是老版本时会失败，**自动回落** PeerJS 老路径（只回落一次）；
- 应急开关：`localStorage["5blong:dc-media"] = "off"`。

其余修复：

| 改了什么 | 为什么 |
|---|---|
| 凭据晚到自愈（`onIceUpgrade`） | 开局 2.5 秒没拿到 `/ice` 就以"纯 STUN"建腿，那条腿永远不去敲中继的门；凭据晚到也用不上（PeerJS 只在 call 那一刻读配置）。现在凭据从无到有时自动拆腿重拨 |
| 兜底补拨遵守发起方向（`shouldCall`） | 约定 `myId < peerId` 一侧发起，但 `ensureCalls` / `onIceUpgrade` 没检查 → 两边每 3 秒互相拨、互相抢答，`calls` 表来回覆盖，最后两边剩的都是"没人应答"那条，`ice = new`。实测 Bink ↔ 爱睡的锦鲤 两边都 `new` |
| 死链一律拆 | 判死链的整段原来套在 `if (mediaAt)` 里，而 `lastMediaAt` 会先被清掉 → 已 closed/failed 的僵尸腿既不算死也不补拨 |
| 重连后自愈计数清零（`resetLinkRetries`） | 自愈只有 3 次，断网 20 秒烧完；重连回来的人**从没离开名册**，走不到任何清零路径 → 两边永久"重新连接" |
| 手动「重新连接」先中继再回落直连 | 原来固定 relay-only，本端没有 TURN 时收集到 0 个候选，点多少次都不可能通 |
| 屏幕共享不再每 12 秒黑一下 | `callScreenPeer` 的僵尸判据只看"发出超过 12 秒"、不看"有没有连上" → 健康呼叫满 12 秒被拆掉重建（观众端就是黑一下→有画面→又黑一下）。改成 `isZombieScreenCall(startedAt, now, connected)` |
| 档位记忆 10 分钟过期 | 记忆无有效期 + 每次新建连接就写回一次 → 一旦降过档 `30fps` 被永久固化。爬回满帧要 18 秒，而呼叫 12 秒就被杀，永远等不到 |
| **ICE 探针**（诊断包新增） | 每条链路带 `gathering` 与 `pairs: { total, succeeded, failed, inProgress, waiting, frozen, relayPairs }`。有对但全 `failed` = 路径确实不通；`total=0` = 候选没交换成功（我们的 bug）。**一次分清 A/B** |

### 四、"自建"现在到哪一层了（重要，别混）

```
第 1 层  信令服务器        ✅ 已自建（server/src/signal.mjs，跑在香港 ECS 9001）
第 2 层  数据通道           ❌ 仍是 peerjs 的 DataConnection
         （自建协商只是**借用**它的 send() 传 SDP，建连/心跳/重连/名册路由都还是 peerjs 管的）
```

并且服务端要双栈兼容老客户端。这是几周的量，不是一晚。

### 🔊 语音：直连只通一边时，自动改走中继

线上实测（房号 009706）：8 人房里 6 个人 RTT 350–440ms、丢包 5–6%，
房主和后进的一位成员出现「他和其他人能说话、和我就连不上」。

根因是两个问题叠在一起，**不是共享屏幕**：

1. ICE 只验证 STUN 包一通一返，**不验证媒体**。对称 NAT 下经常出现
   "ICE 标 connected、实际只有一边有声音"，而且 ICE 一直认为这条腿是好的；
2. 自动自愈重拨 3 次用的都是**同一套候选、同一套策略**，于是永远选回那条单向路
   —— 用户点「重新连接」也是原地打转。

现在：

- **单向检测**（`engine.ts` 的 `checkVoiceLinks`）：每 5 秒看一次
  `inbound-rtp.packetsReceived` 是否在涨。从没收到过 3 次（≈15 秒）、
  收到过又停了 5 次（≈25 秒）就判定"收不到他的声音"。
  闭着麦（`muted`）、本来就没麦克风（`hasMic === false`）的成员自动排除，
  否则会把对端行为当成线路故障反复重拨。
- **改走中继**：判定后拆掉旧链路，重拨时 `iceTransportPolicy: "relay"`，
  只收集中继候选，直接绕开打不通的直连。TURN 本来就有（Cloudflare，`/ice` 现签）。
  实现方式是把 Peer 的 `config` 写成 getter 对象 —— PeerJS 在 `peer.call()`
  的同步段里 `new RTCPeerConnection(config)`，所以设标志 → 拨号 → 复位，
  只影响这一条连接（PeerJS 不支持重协商，`setConfiguration + restartIce` 实测不可靠）。
- 自动自愈第 2 次起改走中继；**手动「重新连接」一律走中继**（用户点它时直连已经失败过）。
- 开黑圈（`game-mesh.ts`）同一套：单向判定本来就有，这次补上"改走中继"，
  通了自动恢复直连优先（省掉中继的额外延迟）。

**共享为什么不是元凶**：共享按设计「观众 ≥3 自动走 SFU」（上行从 N 路变 1 路），
房主只是观众时只收不发，打不满自己的上行。那个房间真正的病是 5% 丢包 + 400ms 延迟。

**服务端 / 数据**

- `worker/accounts-schema.sql` 新增：`friendships.alias`、`friend_requests.note / status`、
  表 `recent_plays` / `knocks` / `daily_actions`。
- **上线前必须跑一次 `npm run accounts:setup`**（幂等 ALTER + 建表），否则新接口会 500。
- 好友快照改成 `toPublicProfile`：不再把对方的固定房号、房号锁定状态、`previousId` 发给别人。
- 敲门复用 `INVITE` 推送类型，**不需要改信令 Worker**（避免单独 `signal:deploy` 的部署顺序坑）。
- 请求量：好友快照「面板开着 20 秒 / 关着 90 秒」，邀请仍是「推送可用 60 秒 / 断开 8 秒」，
  敲门在 8 秒模式下每 8 轮才拉一次；「最近一起玩」只在打开面板时拉。
- 新增 9 条接口测试（重复申请不重推、冷却、删好友不对称冷却、备注名可见性、附言截断、
  最近一起玩过滤、敲门闭环、邀请在线状态、快照不泄露字段），总计 355。

## 最近更新（2026-10-15）

### 1. 进不去房间：换成自建信令服务（1.5.0）

- **现象**：部分测试者一直卡在「没能进入房间 / 与信令服务器的连接中断」，换网络、重试都无效。
- **根因（实测确认）**：信令走的是公共 PeerJS 云（`0.peerjs.com`），它在 **WebSocket 握手**阶段返回  
  **Cloudflare `error code: 1020`**（按浏览器签名封禁）；同一台服务器的普通 HTTP 请求却是 200。  
  也就是说问题不在用户网络，而在第三方服务对我们这类客户端的拦截。  
  （顺带否掉一个"想当然"的方案：借自家域名把请求转发过去**没用**——它连我们 Worker 的服务器请求一起拦。）
- **现在的做法**：**自建信令服务**（`worker/signal/`，Cloudflare Worker + Durable Object，  
  **与 PeerJS 客户端线协议完全兼容**），客户端只连 `wss://5blong.pages.dev/peerjs`，  
  Pages Worker 通过 **service binding（`SIGNAL`）**&#x628A;它转到自建服务——**不过公网、不产生流量费**。  
  **客户端业务代码零改动**，只换了信号服务器地址。
- **成本 0 元**：用 WebSocket **休眠 API**（空闲不计计算时长）+ **心跳自动应答**  
  （PeerJS 每 5 秒一条心跳，精确字符串匹配自动回，不唤醒、不计请求额度）。按每天 100 房 × 5 人估算  
  ≈ 650 次请求/天，免费额度 100,000/天，**用量不到 1%**。
- **信令瞬时抖动会自动恢复**：`network / socket-error / socket-closed` 这类"连接没建起来"的错误  
  不再直接判死，而是**换线路重试 3 次**（退避 0.7s / 1.4s，逐次轮换 自家域名 → 公共云兜底）；  
  首页错误条也加了「再试一次」。注意：`房主不在线`（peer-unavailable）不重试——那是确定性结论。
- **验收（全部通过）**：两端注册 `OPEN` · 消息路由带 `src` 转发 · 目标不存在回 `EXPIRE`  
  （客户端据此提示"房主不在线"）· 断开广播 `LEAVE` · 重复 id 回 `ID-TAKEN`（房主撞码靠它换码重试）。
- ⚠️ **老客户端（≤1.4.8）仍连公共 PeerJS 云**，要更新到 1.4.9 才走自建信令；  
  `*.workers.dev` 在大陆常不可达，所以**自建服务只能经自家域名访问**，不要把 workers.dev 地址发给用户。

### 2. 共享屏幕的系统声音：从"能共享"到"一定有声音"（1.4.8）

- **修：音频轨一断就把整个共享停掉**。原先给 `stream.getTracks()` 全挂了 `ended → 停播`，  
  而 Windows 的系统音频靠 WASAPI 回环采集，对默认输出设备极敏感（7.1 声卡、虚拟声卡、无音频通道的  
  HDMI、蓝牙），音频轨"刚拿到就是结束状态"时会把**本来好好的画面共享一起关掉**——用户看到的就是  
  "一勾系统音频，共享秒消失"。现在只认**画面轨**，音频断了只提示不停播。
- **修：客户端内置系统声音采集**。浏览器拿不到系统音频时（Chromium 对回环端点格式挑剔），  
  客户端在 Rust 侧直接走 **WASAPI 回环**（`AUDCLNT_STREAMFLAGS_AUTOCONVERTPCM`，音频引擎自动把  
  8ch/44.1k 转成 2ch/48k），经 Tauri Channel 流给页面，用 AudioWorklet 播进  
  `MediaStreamAudioDestinationNode`，与画面轨合并发布——**耳机照插 7.1 声卡也能给观众出声**。
- **修：采集线程无声死亡**。根因是 `wasapi` 0.14 的 `read_from_device_to_deque` 在**无数据时**  
  会对空指针做切片（真机探针实测直接 panic），panic 不走错误回调 → 表现为"共享正常但没有声音、  
  也没有任何提示"。现在**有包才读**（`get_next_nbr_frames()`）+ 线程外套 `catch_unwind` 上报 +  
  前端"4 秒没有音频数据即判失败"，这类哑故障不再存在。
- 开关保留（勾不勾由用户决定）；没勾 = 不共享声音。网页端拿不到系统声音时会**引导改用桌面客户端**。

### 3. 音量：把"拉到 200% 也没用"修好（1.5.0）

- 每头猪的走位由房主统一模拟，**每 600ms 广播一次**权威位置，其他端平滑跟随——

- 广播由独立计时线程（Worker）驱动：**房主切后台 / 最小化，访客看到的猪照样在走**，

- 姿态（吃菜 / 被投喂 / 8 种互动 / 空降 / 吊起）本来就是"事件驱动"，天然全房一致；
- 走位朝向带**迟滞判定**，不会出现小猪"倒着走"或高频抖动的现象。

**一天四时段光照**

- 场景随时间自动切换四种光照：**清晨**（淡粉天空）、**白天**（明亮蓝天）、

- **任意窗口尺寸小猪都踩在草地上**：纵深坐标从"舞台相对"改成"视口脚部带"（视口高度

- **公告栏重新布局**：从悬浮定位改为流式排版，**任何分辨率都显示**，不再与其他内容重叠、

**音频处理的生效时机**

- 打开网页 / 客户端时**静默预热 AI 降噪（RNNoise）组件**（不需要麦克风权限），
