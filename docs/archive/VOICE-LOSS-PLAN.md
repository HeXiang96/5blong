# 语音丢包优化方案（2026-11-03 深夜）

> 背景：1.9.19/1.9.20 诊断实测，跨网链路（江苏家庭宽带 ↔ 香港中继 ↔ 兰州校园网）
> 走中继时丢包 **~8%**（收 3326 包 / 丢 279），理想值 1~3%。RTT 136~144ms。
> 目前 `useinbandfec=1`（带内 FEC）已开启，5% 丢包内基本听不出来，8% 会有可感知的断续。

---

## 0. 先搞清楚：丢包发生在哪一段

走中继时的路径是**两段**独立 UDP：

```
你(江苏) ──段A──▶ 香港coturn ──段B──▶ 兰州(校园网)
```

丢包 8% 是两端合计，**段A 和段B 谁贡献的多，决定修哪里**。

**测量方法（不改代码，现有工具就能做）**：
1. coturn 的 verbose 日志按会话统计 rp/rb —— 有会话级收发计数；
2. 诊断包里每条腿有 `loss_pct`（各自的丢包）—— 对比两个人的数字：
   - 你的丢包 ≈ 段A 丢包；兰州的丢包 ≈ 段B 丢包；
3. 也可以在**两个端各自 ping/mtr 香港中继**，直接看路径质量（ICMP 与 UDP 不完全等价，但趋势可信）。

**先测再花钱**：如果段A、段B 都 4~5%，是跨境链路整体的问题 → 方案 A；
如果只有段B（兰州→香港）差，校园网出口问题 → 方案 A 收益更大，或方案 B 试探。

---

## 1. 方案 A：国内中继节点（治本，推荐）

**原理**：丢包的主源头是**跨境 UDP**。运营商对国际方向 UDP 的限速/丢包在晚高峰
明显重于国内方向。国内中继把"跨境"变成"国内"，物理上绕开这段。

```
你(江苏) ──▶ 杭州coturn ◀──兰州(校园网)      ← 两人到国内都稳
            （/ice 同时下发香港+杭州，ICE 自动择优）
```

| 项 | 说明 |
|---|---|
| 规格 | 阿里云杭州**轻量应用服务器**，2核2G 足够（只跑 coturn） |
| 成本 | 几十~一百多元/月；语音 40kbps，13 人房满载约 6Mbps，按流量计费也便宜 |
| 备案 | 一般**不需要**（不占 80/443 做网页服务，只跑 3478/5349/50000-50999）——下单前跟客服确认一句 |
| 改动 | 服务器侧：新机装 coturn + 同一套静态凭据；`/ice` 加一条 TURN 地址。**不用发版**（ICE 列表是服务器下发的） |
| 风险 | 低：香港中继保留作备选，ICE 自动择优；国内节点挂了自动回落香港 |
| 效果预期 | 跨网丢包从 ~8% 降到 1~3%（国内方向 UDP 质量与教育网内部接近） |

**何时做**：丢包确认主要来自跨境段、且听感确实受影响时。这是唯一动网络层的方案。

---

## 2. 方案 B：TURN 上 443（SNI 分流）——治端口，顺带可能改善丢包

**原理**：有些网络对 3478/50000+ 的高位 UDP 特别狠，但对 443 温柔。
把 TURN 的 TLS 入口挪到 443（nginx 按 SNI 分流给 coturn），任何"只放行 443"的
网络都能走通。

| 项 | 说明 |
|---|---|
| 成本 | 0 元（纯服务器配置） |
| 改动 | 装 nginx stream 模块 + DNS 加 `turn.5blong.site` + 签证书 + `/ice` 加 `turns:turn.5blong.site:443`。**不用发版** |
| 风险 | 中：动 nginx 的 443 入口，要按"备份→`nginx -t`→reload→一键回滚"操作 |
| 效果预期 | 主要解决**端口封锁**型不通；对丢包改善取决于 ISP 对 443 与高位 UDP 的区别对待，**不保证** |

**何时做**：遇到"只放行 443"的网络时再做。不作为丢包的首选方案。

---

## 3. 方案 C：软件层自适应（治标，收益有限但免费）

已做的：
- `useinbandfec=1`（带内 FEC）：丢包 5% 内"偶尔卡"vs"听不出"的分界，**已开启**；
- 1.9.20：单通/抖动不再拆腿重拨（避免把丢包问题变成断线循环）。

还能做的（按性价比）：

| 优化 | 说明 | 收益 | 代价 |
|---|---|---|---|
| **丢包自适应码率** | 丢包 >5% 时主动降 Opus 码率（64k→32k），腾出带宽给 FEC | FEC 在低码率下保护效率更高，高丢包时听感改善明显 | 音质略降（语音 32k 依然清晰） |
| **DTX 关闭确认** | `usedtx=0` 已关——保持。DTX 省的带宽不值得在丢包链路上增加状态复杂度 | —— | —— |
| **RED 冗余编码** | 每个 RTP 包携带前 20ms 的冗余副本 | 抗 20~30% 突发丢包 | 带宽 ×~1.6；Chrome 对 Opus 的 RED 支持有限，需验证 |
| **接收端 jitterBuffer 微调** | 调 playoutDelay 换抗抖动 | 晚高峰抖动场景顺播更稳 | 延迟 +20~60ms |

**何时做**：方案 A 落地后如果还想要更好，或不想花钱时先做"丢包自适应码率"
（改动小：`audio-profile.ts` 里按运行时丢包率切 profile，半天工作量）。

- ✅ `useinbandfec=1`（带内 FEC）

## 5. 推荐路线

```
第一步（本周，0 元）：测量——两人各 ping/mtr 8.210.198.140，对比丢包数字
                     + 房间里各提交一次反馈，对比两人的 loss_pct
        ↓ 确认丢包主要在跨境段
第二步（下周，~100元/月）：买杭州轻量服务器跑 coturn，/ice 加一条地址
        ↓ 全员不动任何设置，ICE 自动择优
第三步（可选，0 元）：丢包自适应码率（若跨网听感仍想再榨一点）
```

**决策点在第一步**：如果测量显示丢包不在跨境段（比如你在国内方向也丢），
那方案 A 的钱要重新评估——先测，再花。
