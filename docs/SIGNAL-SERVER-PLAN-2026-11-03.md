# 自写信令服务方案（替代开源 `peer` 包）

> 2026-11-03 · 只给方案，未动任何代码
> 现状：信令跑在自建香港 ECS 上，进程 `5blong-peer` 用的是 npm `peer` 包（`server/src/peer.mjs`，136 行）。

---

## 0. 一句话结论

**能换，而且是长期正解；但今晚不该换。**

自写信令能解决「后台看不见 / 两张注册表 / 超时不可控」；
**不能**解决「访客关掉客户端后房主一直显示重连中」——那个判断在客户端里，协议里也没有"某人走了"这种推送。

---

## 1. 为什么想换（对比 CF 时代）

| 维度 | CF 时代 | 现在（自建 + `peer` 包） |
|---|---|---|
| 谁在哪个房 | 服务端自己知道 | 服务端只认 `5b-h-<房号>` 这个 id，**不知道房里有谁** |
| 房号注册表 | 一张（CF Worker） | 两张（自建 + 公共云兜底），互不相通 |
| 断线感知 | 服务端 socket 关闭即可知道 | 同样知道，但**没法告诉老客户端** |
| 心跳超时 | 自己定 | 依赖包参数 `alive_timeout` |
| 后台数据 | 服务端直接给 | 只能靠房主客户端 HTTP 上报（今天一整天的坑都出在这） |

---

## 2. 目标 / 非目标

### 目标

1. **后台不再依赖客户端上报**：房号在线、房里几个人、谁和谁在握手，服务端自己算。
2. **一张注册表**：兜底线路也指向自己（或多节点共享注册表），彻底消掉"房主不在线"。
3. **超时/限流自己控**：`alive_timeout`、单 IP 建房频率、单房人数上限都可精确配置。
4. **可观测**：`GET /rooms-live` 直接给 JSON，后台和运维脚本共用。

### 非目标（明确不做，避免预期落空）

1. ❌ 不解决"访客关掉后房主名册不退出"——需要改客户端（`tickLiveness` 以名册为准清理），是另一件事。
2. ❌ 不做多机房/多活（单机 + 单注册表足够，13 人房最多几十个连接）。
3. ❌ 不改客户端离线能力（老客户端必须继续能用，这是硬约束）。

---

## 3. 协议契约（这是全部风险所在）

客户端已经装出去，服务端必须**逐字节兼容** PeerJS 1.x 的信令层。

### 3.1 握手

```
wss://5blong.site/peerjs?key=peerjs&id=<我的id>&token=<随机串>&version=1.5.5
```

- `id` 已由客户端指定（`5b-h-<房号>` 房主 / `5b-g-<随机>` 访客）；
- 重复 id → 必须回 `ID-TAKEN` 并关闭旧连接（客户端依赖这个错误码决定换 id 重试）；
- id 不合规 → `INVALID-ID`。

### 3.2 消息类型

| 类型 | 方向 | 服务端要做的事 |
|---|---|---|
| `OFFER` | C→S→C | 按 `dst` 转发；`dst` 不存在回 `EXPIRE`；`src` 必须改写成真实 id（防伪造） |
| `ANSWER` | C→S→C | 同上 |
| `CANDIDATE` | C→S→C | 同上（ICE 候选，量大，需限速） |
| `LEAVE` | C→S | 从注册表摘除，通知对端（可选） |
| `HEARTBEAT` | C→S | 回 `HEARTBEAT`；刷新该连接 `lastSeen` |
| `EXPIRE` | S→C | 目标不存在时下发 |
| `ID-TAKEN` | S→C | id 冲突时下发 |
| `OFFER/ANSWER/CANDIDATE` 之外的未知类型 | — | **必须静默忽略**，不能抛错断开（老客户端可能发新字段） |

### 3.3 断开语义

- socket 关闭 → 摘注册表 → 记录"该 id 的时间线"（给后台用）；
- 不做广播（老客户端不认识），但写进 `/rooms-live`。

### 3.4 兼容性硬约束

- `GET /peerjs/id` 需返回一个随机 id（个别客户端会调用）；
- `GET /peerjs/peers` 必须 401/403（不能暴露 peer 列表）；
- nginx 已有 `/peerjs` → `127.0.0.1:9000` 的反代，路径与 `Upgrade` 头保持不变。

---

## 4. 服务端设计（单文件、可替换）

```
server/src/signal/
  protocol.mjs   消息编解码 + 类型校验（纯函数，最好测）
  registry.mjs   id → conn 的注册表；事件：connect / disconnect / message
  rooms.mjs      从 OFFER/ANSWER 的 src→dst 推导「谁在跟哪个房号握手」
  server.mjs     ws 服务 + 心跳 + 限流（替换 peer.mjs 的 startPeerServer）
```

- 依赖只有 `ws`（极小），不引入框架；
- 注册表在**进程内存**，重启即清空（客户端会自动重连，和今天一样）；
- `/rooms-live` 由 `rooms.mjs` 直接吐 JSON，后台 `admin.mjs` 读它，不再读客户端上报文件；
- 保留现有观测钩子（`live-rooms.json`）作为过渡期双保险。

---

## 5. 三阶段实施（风险从低到高）

### P1 · 只读代理（半天，零协议风险）

```
客户端 → nginx → 代理(新增) → 现有 peer 进程
                    └─ 顺手记 src→dst、连接生死，写 /rooms-live
```

- 转发逻辑一行不改，出错最多是"日志不准"；
- 收益：后台立刻能看到"850122 里此刻 3 个人、谁在和谁建链"；
- **这一阶段我可以先做，不用等自写。**

### P2 · 自写实例跑影子（1 天）

- 绑定 `127.0.0.1:9001`，用测试客户端跑完整用例（见 §6）；
- 同时用真实客户端连一次（它会在另一张表上，不影响生产）；
- 跑通再进 P3。

### P3 · 切换（30 分钟，可回滚）

- 改 nginx upstream 到 `9001`，`nginx -t && reload`；
- 观察 10 分钟：连接数、错误率、`/rooms-live`；
- 异常 → 改回 `9000` 再 reload，10 秒恢复。

> ⚠️ **不能灰度**：id 注册表必须唯一，两个服务各存一半 = 重现今天的"两张表"。

## 6. 验收清单（P2 必须全绿才允许 P3）

| # | 用例 | 通过标准 |
|---|---|---|
| 1 | 建临时房 | 房主 id 注册成功，`/rooms-live` 出现该房号 |
| 2 | 访客用房间码加入 | 访客 id 注册、OFFER 到达房主、ANSWER 回传 |
| 3 | 访客断网 20 秒后恢复 | 自动重连成功，房主名册不重复、不残留 |
| 4 | 同名 id 二次登录 | 旧连接收到 `ID-TAKEN`，新连接正常 |
| 5 | 加入不存在的房号 | 访客收到 `EXPIRE`，界面提示"房主不在线" |
| 6 | 13 人房 | 12 条访客连接，无消息丢失、CPU < 20% |
| 7 | 双击/刷新页面 | 旧 socket 关闭后注册表无残留 |
| 8 | 挂机 30 分钟不动 | 心跳维持，不被误踢 |
| 9 | 大文件共享屏幕（P2P 数据） | 信令只转发 SDP/候选，带宽占用可忽略 |

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 漏实现某个消息类型 | **全员连不上** | P2 用真实客户端回归；未知类型静默忽略；保留 `peer` 包随时切回 |
| 心跳语义不一致 | 挂机被误踢 或 死连接不清 | 用今天实测的客户端行为校准（客户端 5 秒一次心跳） |
| 候选消息量大 | 单进程 CPU 打满 | `CANDIDATE` 走直通转发、不做 JSON 深拷贝；单房上限 13 人 |
| 重启丢注册表 | 所有人断线重连 | 与现在一致（`peer` 包同样是内存表），客户端有重连逻辑 |
| 无法灰度 | 切换即全量 | 保留旧进程、nginx 一行回滚；选在低峰（凌晨）切 |

## 9. 需要你拍板的三件事

1. **优先级**：先做 P1（半天拿到"后台实时成员"），还是直接排 P2+P3？
2. **兜底策略**：自写信令上线后，公共云兜底是**删掉**还是**也指向自己**（需要多节点时再谈）？
3. **切换窗口**：允许在凌晨做一次 10 分钟的全量切换吗？（不能灰度，只能一次性）

## 10. 与今天修复的关系

- `1.9.18`（已上线）修的是客户端：凭据自愈、重拨间隔、跨线路重试、画面僵尸判定、档位记忆、上报守卫、版本号；
- 本方案修的是**服务端架构**：后台数据来源、注册表数量、超时可控；
- 两者不冲突，且顺序应该是「先客户端止血，再服务端换心脏」。
